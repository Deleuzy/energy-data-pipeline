# energy-data-pipeline

A small, tested pipeline for Danish grid CO2 data: it fetches public data from
Energinet's [Energi Data Service](https://www.energidataservice.dk/), checks it
with explicit rules, stores raw, validated and flagged rows in SQLite, and
calculates location-based scope 2 emissions for a site's electricity use. It runs
as a plain CLI or as a Dagster asset graph, and serves results through FastAPI and
a static HTML dashboard.

```
Energi Data Service ──► fetch (cached, rate-limited) ──► validate (rules, nothing dropped)
                                                             │
         dashboard.html ◄── report ◄── scope 2 ◄── SQLite (raw / validated / flags)
                                                             │
                                                        FastAPI
```

## What is real and what is synthetic

| Part | Status |
|---|---|
| CO2 intensity (`CO2Emis`) | **Real.** Energinet, 5-minute g CO2/kWh of consumed electricity, DK1 and DK2 |
| Consumption, wind, solar (`ProductionConsumptionSettlement`) | **Real.** Energinet, hourly MWh per price area |
| Test fixtures in `tests/fixtures/raw/` | **Real.** A 3-hour slice (2026-10-13 06:00–09:00 UTC) saved from the API |
| Defects in `tests/test_validate.py` (duplicates, negatives, jumps…) | Hand-made frames in the tests, used to prove each rule fires |
| Example site (`examples/synthetic_site_hourly.csv`, `..._monthly.csv`) | **SYNTHETIC.** An invented office profile, generated by `examples/make_synthetic_site.py` (seed 42). Not a real site |

So the scope 2 number below is real intensity multiplied by invented consumption.
It shows the method, not anyone's footprint.

## Validation rules

Every row comes out of validation with `quality` = `ok`, `warning` or `error` and
the list of rules it broke. Missing slots are inserted as empty rows so the gap is
visible. Flagged rows are never dropped; each finding is also a row in
`quality_flags`.

| Rule | Severity | Applied to |
|---|---|---|
| `missing_slot` – expected 5-min / hourly slot absent (incl. a whole price area) | error | all |
| `duplicate` – more than one record per slot and area (all copies kept) | warning | all |
| `null_value` | error | all |
| `negative_value` | error | CO2, consumption, wind, solar |
| `out_of_range` – CO2 outside 0–1000 g/kWh, consumption outside 0–10,000 MWh | error | CO2, consumption |
| `sudden_jump` – CO2 hourly change > 75 g/kWh; consumption change > 35 % (not across gaps) | warning | hourly series |
| `incomplete_hour` – hourly CO2 built from fewer than 12 usable 5-min values | warning | CO2 hourly |
| `outside_window` – record outside the requested time window | warning | all |

The thresholds are my own design choices for this demo, not limits published by
Energinet. The hourly CO2 value is the mean of the 5-minute values in that hour
that carry no error flag.

## Scope 2 calculation

Location-based: `kg CO2 = Σ kWh(hour) × intensity(hour) [g/kWh] / 1000`, using the
hourly intensity of the site's price area. Hours with no usable intensity (missing,
or flagged as error) are **not filled in**; their kWh are reported as not covered,
with the list of hours, so the gap is visible. Hours with warnings are used.
A monthly CSV (`month,kwh`) is multiplied by the plain monthly mean intensity,
which ignores when in the month the power was used; the output labels it as an
approximation.

Input CSV: `timestamp_utc,kwh` (hourly) or `month,kwh` (`YYYY-MM`). Lines
starting with `#` are comments.

## Storage

SQLite (`data/energy.db`), schema in [`src/edp/store.py`](src/edp/store.py):

- `fetch_log` – request URL, fetch time, record count, SHA-256 of each cached page
- `raw_co2emis`, `raw_production_consumption` – records as returned by the API
- `co2_5min_validated`, `co2_hourly`, `consumption_hourly` – validated series with quality labels
- `quality_flags` – one row per finding
- `runs` – run id and window

Each run replaces the previous one, so the database always holds the latest run.
Raw API responses are cached as JSON under `data/raw/<dataset>/` with a
`.meta.json` next to each page.

## How to run

```bash
uv venv -p 3.12 .venv && uv pip install -p .venv/bin/python -e ".[dagster,dev]"
```

Plain CLI (fetches live data the first time, then uses the cache):

```bash
.venv/bin/edp run --start 2026-10-01T00:00 --end 2026-10-15T00:00
```

Scope 2 for your own CSV against the stored intensity:

```bash
.venv/bin/edp scope2 examples/synthetic_site_monthly.csv --area DK1
```

Dagster (asset graph `co2emis_raw`, `production_consumption_raw` → `validated` → `sqlite_db` → `report`):

```bash
.venv/bin/dagster dev -m edp.definitions
```

API (after a run), docs at `http://127.0.0.1:8000/docs`:

```bash
.venv/bin/edp serve
```

- `GET /intensity?area=DK1&start=2026-10-01T00:00:00&end=2026-10-02T00:00:00`
- `GET /quality`
- `POST /scope2?area=DK1` with a CSV file upload
- `GET /dashboard`

Tests (offline, no network):

```bash
.venv/bin/pytest -q
```

26 tests cover the fetch cache and pagination, each validation rule, the scope 2
maths, the full pipeline on the saved real slice, the Dagster assets and the API.
They pass on Python 3.11 (pandas 2.3) and 3.12 (pandas 3.0). GitHub Actions runs
them on both versions (`.github/workflows/ci.yml`).

Docker: `docker build -t edp . && docker run -p 8000:8000 edp` runs one live fetch
and then serves the API. The Dockerfile has not been built yet in this repo.

## Limitations

- `CO2Emis` is Energinet's near-real-time figure. Energinet notes that it is based
  on upscaled real-time measurements, that errors occur and are generally not
  corrected, and points to `DeclarationGridEmission` for the settled figures. A
  reporting-grade scope 2 should use the declared figures; this demo does not yet.
- Location-based only. Market-based scope 2 (contracts, guarantees of origin) is
  not covered.
- `ProductionConsumptionSettlement` is published with a delay of roughly ten days,
  which is why the default window ends on 2026-10-15.
- The rules catch structural problems (gaps, duplicates, impossible values, large
  jumps). They cannot tell whether a plausible-looking value is wrong.
- Thresholds were set by hand and have not been tuned on a longer history.
- One run, one 14-day window. The dashboard loads plotly.js from a CDN, so viewing
  it needs internet access.
